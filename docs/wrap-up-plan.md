## 三、收尾前必须先解决的 3 个阻塞项

### 阻塞 1｜Node 运行时版本已变更，工具链静默失效 ⚠️

- 版本从 `22.22.2-3` 变为 **`22.22.2-6`**，旧路径已不存在。
- 后果：用旧路径调用任何脚本都会**静默失败**——不报错、无输出、文件不生成。今天上午我因此连续误判了三次（以为 `validate-books` 跑过了、`data-lint C2` 跑了、`run-pipeline` 只是环境问题），实际全部是空跑。
- `run-pipeline.mjs:4` **硬编码**了旧路径，因此这个一键健康检查脚本现在**永久失效**。
- 项目记忆里记录的路径同样已过期。

修复：改 `run-pipeline.mjs` 的 `NODE` 常量；更稳妥的做法是加一个 `_node.mjs` 探测可用版本，避免以后升级再踩同一个坑。

### 阻塞 2｜「B2 例句补充」自动化仍在空转

- 该自动化**仍在运行**（今天 14:55 刚跑完第 64 轮），但已连续数十轮**零写入**：
  全池可用真词仅 11 条，上限约 21 条 ≪ 150，且用 50 条定向探针 + 117 条盲抽样复核**命中 0**。
- 结论：B2 的例句补全这条路**已经走到尽头**，不是"再坚持几批"能解决的。
- 处理：暂停它。它现在唯一的产出是每小时消耗一次机时。

（「词书扩容」自动化自 10/07 起已停止写入，不再是活跃污染源，但仍建议确认它不会在清理期间复活。）

### 阻塞 3｜无 git / 无备份

13 天里 `books.js` 被外部并发改写多次，无法追溯、无法回滚。这是所有"数据事故"至今无法收拾的根因。

## 四、三个收尾档位（请选一个）

### 方案 A：最小可发布 ✅ 推荐

目标：**能公开给用户用，不出错、不掉链子**。不追求词库完整。

| 步骤 | 内容 | 验收标准 |
|---|---|---|
| A1 | 停掉两个自动化 | 24 小时内 `books.js` 无外部写入 |
| A2 | 建 git 仓库，首次提交当前状态 | `git log` 有基线提交，可回滚 |
| A3 | 修 `run-pipeline.mjs` 路径 + 重跑健康检查 | 一键脚本 exit 0，smoke 128 ✓ |
| A4 | UI 隐藏 C1/C2，词书卡标注真实例句覆盖率 | 选词书时能看出哪本"内容就绪" |
| A5 | 修 84 条释义无汉字/乱码 | 全库 `释义无汉字 = 0` |
| A6 | 修 B2 67 条已知错义（bendito/mocoso/bronceado/juerga…） | 抽查 50 词无误义 |
| A7 | 认词卡对"无例句词"给明确提示，不再给 `___ es una palabra.` 假题 | C1/C2 词卡显示"该词暂无例句" |

预估：1–2 个工作日。

### 方案 B：A + B2/C1 内容达标

在 A 之上追加：删除 pass 清理 B2/C1 的非词条 → 给清理后的词补例句。

**代价（必须先说清）**：
- 删除 pass 必须先加固正则——历史事故：`[^}]*` 会把含 `}` 的条目截断成半截。
- 例句按 150 条/批，补满 B2 剩 1,939 条 + C1 需先清理后重估，约 20+ 批。
- 实测成本极高：B2 补例句自动化连续数十轮产出趋近 0。

预估：2–3 周，且需要持续人工挑选，不适合"收尾"阶段。

### 方案 C：按真实 CEFR 词表重建词库

最彻底，但工作量最大、风险最高。**不建议在收尾阶段做**——它是一次重写，不是收尾。

---

## 五、为什么推荐 A

1. **收尾的目标是"稳"，不是"全"。** 现在最大的风险是"用户点进 C2 看到 `six`/`beacon`"，而不是"B2 少 1,939 条例句"。
2. **成本收益倒挂**：把 B2/C1 例句补满需要 20+ 批人工，而隐藏 C1/C2 只需要 1 行代码就能消除 23,760 个词的体验风险。
3. **不破坏已有资产**：A 方案不删任何词，随时可以反悔；B/C 方案一旦删错且无 git，无法挽回。
